# Whilo — auditoria S+ independente: dados, Supabase e event model

**Parecer: a fundação de persistência e recuperação é útil, mas este eixo ainda não satisfaz S+ nem demonstra uma integração Supabase pronta para produção. Nota: 5/10.** Whilo já tem um adaptador que executa em PGlite local ou PostgreSQL remoto, compare-and-swap para transições críticas, leases/checkpoints de tarefas, alguma idempotência e comportamento conservador para ações cujo resultado externo ficou incerto. Porém, a produção descrita em `docs/STACK-ARCHITECTURE.md` é um alvo, não o estado demonstrado pelo código: não encontrei cliente/configuração Supabase, migrations Supabase, RLS, Storage, Auth Supabase ou Realtime ligados ao app. O modelo de dados principal continua sendo uma única tabela genérica `records` com `jsonb`; histórico de eventos não é uma sequência imutável/reexecutável, e os arquivos são locais ao host. Avaliação estática do commit local `9aa69c3`, em 3 de outubro de 2026; não alterei código de produção nem executei serviços externos.

## Estado por capacidade

- **Já existe — persistência local e PostgreSQL genérico.** `createStore()` cria PGlite quando não recebe DSN; é persistente em disco quando recebe `dataDir` (como no `apps/server/src/index.ts:7-10`) e em memória nos testes sem diretório. Com `DATABASE_URL`, usa `pg.Pool`; ambos expõem as mesmas operações da `Store` (`apps/server/src/db.ts:13-76,115-142`). A tabela é criada no boot como `records(owner,kind,id,data jsonb,updated_at)` com chave `(owner,kind,id)` (`db.ts:138-141`). PGlite é PostgreSQL embutido em WASM, suportado para uso local/testes; isso não o transforma em Supabase Auth, RLS ou Realtime [1].
- **Já existe — isolamento pelo serviço e controles atômicos úteis.** Leituras/escritas normais levam `owner` em seus predicados; a chave da tabela também inclui owner. O middleware resolve o owner da sessão antes de montar o contexto do Hono (`apps/server/src/app.ts:506-517`; `apps/server/src/auth.ts:17-45`). `compareAndSwap`, `insertIfAbsent` e `claim` usam predicados SQL condicionais (`db.ts:47-69,78-89`). Há teste de isolamento de task entre dois owners e testes reais com PGlite para claim concorrente, checkpoint pós-restart e idempotência concorrente de action (`tests/agent-api.test.ts:105-140`; `tests/engine.test.ts:30-98`; `tests/actions.test.ts:50-68,216-248`).
- **Parcial — idempotência.** Tasks podem receber chave interna e Actions podem receber chave; o identificador é estável e a inserção é atômica (`apps/server/src/engine/service.ts:180-229`; `apps/server/src/actions.ts:39-99`). Os testes cobrem reuso da mesma chave e concorrência. Nenhum dos dois fluxos vincula a chave a um fingerprint da requisição antes de retornar o registro existente: a mesma chave com prompt/payload diferente recebe silenciosamente a operação antiga (`service.ts:184-186`; `actions.ts:45-52`). A rota pública de criação de task também não aceita chave idempotente (`apps/server/src/engine/routes.ts:28-55`).
- **Parcial — recovery de tasks e ações.** O task worker persiste checkpoints no task, reivindica lease por CAS, renova o lease e recupera tasks `running` vencidas no próximo polling; o teste valida restauração do checkpoint (`apps/server/src/engine/worker.ts:75-131,141-179`; `tests/engine.test.ts:70-98`). Actions são reivindicadas uma vez, e o restart classifica `executing` como `outcome_unknown`, evitando retry cego (`apps/server/src/actions.ts:150-190`; `db.ts:91-94`; `apps/server/src/index.ts:6-12`). Ainda assim, recovery e histórico têm falhas descritas abaixo.
- **Parcial — artifacts, eventos e audit.** Tasks, runs, `run-events`, artifacts estruturados, actions e atividade são persistidos como records. O detalhe do task reconsulta e ordena eventos por data (`apps/server/src/engine/service.ts:160-178`); artifacts estruturados recebem ID derivado de task/chave (`service.ts:672-691`). Há também `O1AuditLedger`, com owner, categoria, target e redação de segredos (`apps/server/src/o1/audit-ledger.ts:7-35`). Isso forma uma base de histórico e inspeção, mas a imutabilidade, ordenação, correlação e deduplicação não são garantidas pelo schema.
- **Ausente — integração Supabase ativa.** A arquitetura documenta Supabase Postgres/Auth/Storage/Realtime e políticas RLS como intenção (`docs/STACK-ARCHITECTURE.md:21-26`), e reconhece que ativação exige URL/chave externa (`:47-49`). As dependências de `package.json` incluem PGlite e `pg`, não `@supabase/supabase-js`; não encontrei migrations do app nem políticas RLS. Há migrations dentro da árvore `openbot/`, que é referência OpenBot separada; elas não são usadas por `apps/server/src/db.ts`.
- **Ausente — event model de replay/audit durável com cursor e outbox; Realtime.** `RunEvent` contém `id`, `taskId`, data, kind, título e detalhe, sem `runId`, sequência monotônica ou chave de dedupe (`packages/domain/src/agent.ts:49-56`). A UI atual consulta o snapshot inteiro a cada 3 s (`apps/mobile/src/agent-workspace.tsx:44-73`); o detalhe é obtido por HTTP e reage ao `task.updatedAt` (`apps/mobile/src/agent-ui.tsx:290-312`). Não há subscrição Supabase.

## Achados de maior impacto

### 1. `records` é um envelope genérico, não um esquema transacional versionado

O SQL inline de `createStore()` cria só `records` e sua PK composta. Não há migrations versionadas, índices dedicados para `kind/status/nextRunAt`, FKs, CHECK constraints ou validação do estado persistido (`apps/server/src/db.ts:122-141`). Os tipos em `packages/domain/src/agent.ts` e `packages/domain/src/index.ts` descrevem shapes TypeScript/Zod para a API, mas não obrigam rows `jsonb` lidas por processos antigos, migrations ou chamadas de servidor a obedecer às mesmas transições. `Store.put()` pode substituir qualquer record; `compareAndSwap()` faz merge JSONB genérico, não restringe campos ou transições permitidas (`db.ts:33-58`). A chave `(owner,kind,id)` protege colisões dentro do mesmo namespace, mas não pode fazer FK entre task, action, event e artifact.

Isso é adequado para evolução rápida/local e facilita manter o mesmo código em PGlite/Postgres. Não equivale a schema governado em Supabase. A divergência de schema entre versões de API/worker, consultas sem índice e limpeza/cascata de registros órfãos se tornam risco de produção. A recomendação é **expandir e migrar gradualmente**, não trocar o banco às cegas: adicionar migration versionada e tabelas tipadas para o núcleo de task/event/action/artifact; manter `jsonb` em `input`, `state` e payloads realmente variáveis; deixar uma tabela de compatibilidade/arquivo `legacy_records` imutável durante o período de rollback.

### 2. Owner scoping é enforcement da aplicação, não RLS

O owner atual é uma string resolvida por sessão interna: `Auth.session()` usa `local-user` ou o valor arbitrário configurado em `accessIdentities`, e cria token bearer opaco salvo em `records` (`apps/server/src/auth.ts:17-45`). Não há ligação a `auth.users.id`. A API limita o acesso ao owner via middleware e métodos da Store, e os testes atestam esse caminho. Isso é um controle real e valioso, mas todas as garantias dependem do caminho Hono chamar o método correto. `Store.scan(kind)` deliberadamente lê todos os owners para workers/manutenção, e a recuperação global também varre records (`db.ts:71-76,91-94`; `apps/server/src/engine/service.ts:73-112`).

Para Supabase, primeiro é preciso decidir se o app passará a usar Supabase Auth ou manterá Auth próprio. `auth.uid()` só representa uma identidade Supabase/JWT verificada; políticas de RLS têm de cobrir SELECT/INSERT/UPDATE/DELETE, com `USING` e `WITH CHECK`, grants mínimos e teste negativo por owner [2]. Secret/service role ignora RLS; portanto, RLS não protege queries que o servidor fizer com uma credencial que bypassa policies [2]. Não prometer que “RLS isola o backend” se o worker continuar usando uma credencial administrativa. Separe as operações de cliente/user JWT das operações privilegiadas de worker, e faça o contrato de privilégio explícito.

**Dependência de migração:** mapear cada owner string atual para identidade UUID autenticada; `local-user`, nomes de access identity e o owner especial `system` não podem ser convertidos por cast. Preserve uma tabela de mapeamento legado, valide colisões e não mescle usuários com base somente em email sem reconciliação autenticada. Mova heartbeat/configuração do worker para tabela de sistema fora das tabelas expostas a clientes.

### 3. Reuso de chave não prova que o retry seja da mesma operação

`ActionService.propose()` calcula `id` a partir da chave e retorna `existing` antes de validar/preparar a entrada nova (`apps/server/src/actions.ts:39-57`). O `hash` salvo em `ActionProposal` protege a revisão/aprovação dos dados já preparados; ele **não** é comparado com o novo payload no caminho idempotente. `AgentService.createTask()` também retorna a task existente só pelo ID derivado da chave, sem comparar `raw` à entrada persistida (`apps/server/src/engine/service.ts:180-229`). `insertIfAbsent` e o CAS das ações evitam duas gravações/duas aprovações concorrentes, o que é positivo, mas não detectam reuso de uma chave para payload diferente. O endpoint HTTP de task sequer aceita idempotency key. Testes cobrem replay igual, não payload conflitante (`tests/actions.test.ts:216-248`).

Adicionar `idempotency_keys(owner_id, operation, key_hash, request_hash, resource_id, created_at, expires_at)` com unique `(owner_id,operation,key_hash)`. Criar o registro junto com o recurso na mesma transação. Retry com mesmo `request_hash` devolve o mesmo resultado; a mesma chave com hash diferente retorna `409` e não chama provider. Guardar hash da chave, não a chave crua. Gerar IDs estáveis por task/run/tool invocation e propagar `provider_idempotency_key` apenas em integrações que documentem suporte. Para provider sem consulta/recibo/idempotência, manter `outcome_unknown` e reconciliação humana; não prometer exactly-once externo.

### 4. Recovery de actions é prudente, mas a recuperação global pode marcar trabalho vivo como incerto

A transição de action de `awaiting_review` para `executing` é um UPDATE condicional, com verificação do task associado; testes confirmam que aprovações concorrentes chamam o provider só uma vez (`apps/server/src/db.ts:78-89`; `apps/server/src/actions.ts:150-190`; `tests/actions.test.ts:50-68`). Depois da chamada, o estado é salvo. Se processo cair após o side effect e antes do save, `outcome_unknown` evita duplicação automática. Isso é a semântica correta de segurança.

O problema é que `recoverInterruptedActions()` marca **todas** as rows `executing` como unknown, sem owner de lease, `started_at`, idade, executor, lock ou fencing token (`db.ts:91-94`), e `apps/server/src/index.ts:7-12` chama isso em todo boot da API. Um novo replica/API boot pode classificar como incerta uma ação que ainda está sendo executada por outro processo. A atualização tampouco grava evento/atividade correspondente. Adicionar `execution_id`, `worker_id`, `lease_until` definido pelo relógio do banco e versões de transição; a reconciliação deve atuar somente em lease expirado, emitir evento durável, e preservar o estado unknown quando o envio pode ter chegado ao provider.

Tasks também têm um recovery útil, mas não reconciliam a row antiga de `runs` se o processo morreu sem executar `catch`: worker reclaims task vencida e abre novo run, enquanto `runs.status='running'` antigo pode permanecer assim (`apps/server/src/engine/worker.ts:116-203,204-241`). No claim/recovery, fechar o run vencido como `interrupted` e gravar evento de recovery, na mesma transação que cria novo lease/run. Use hora do banco para claim, vencimento e heartbeat; `TaskWorker` hoje escreve/avalia lease usando relógio Node (`worker.ts:118-130,166-182`).

### 5. `RunEvent` é persistido, mas não forma um log de replay/audit imutável

`TaskContext.event()` cria UUID aleatório e grava cada evento com `Store.put()` em outro comando, sem `runId` nem sequência (`apps/server/src/engine/worker.ts:154-164`). Task checkpoint, run row e evento também são writes separados (`worker.ts:184-203`). Queda entre esses writes pode deixar task sem evento de transição, event sem checkpoint correspondente ou run órfão. A tela retorna todos os eventos, em vez de páginas/cursor, e ordena por `date`; timestamps iguais não têm ordenação de domínio garantida (`apps/server/src/engine/service.ts:160-178`). Como `put` é upsert e não há trigger/privilege que impeça UPDATE/DELETE, “event” não significa imutabilidade do banco.

`O1AuditLedger` acrescenta eventos com payload redigido, mas usa `randomUUID()` por chamada e o `Store` ainda permite alteração/deleção. A trilha também está separada de `run-events`, `activity`, `runs` e `actions` (`apps/server/src/o1/audit-ledger.ts:20-35`; `apps/server/src/actions.ts:192-201`). Não há um único fluxo correlacionável para resposta: actor, task, run, ação/provedor, sequência e estado final.

Adotar snapshot mutável de `tasks` **mais** log append-only `task_events`; não é necessário event-sourcing integral para o MVP. Cada evento deve ter `(owner_id, task_id, sequence)`, `event_id`, `run_id`, `type`, payload minimizado, `occurred_at` do banco e chave idempotente de origem; unique `(owner_id,task_id,sequence)` e unique em `event_id`/chave da operação. Transação única para claim/run, mudança de estado e evento crítico. Escritas append-only apenas para o papel que grava; revogar UPDATE/DELETE do papel de aplicação e, se necessário, arquivar por política de retenção documentada. Disponibilizar `GET /tasks/:id/events?after=<cursor>&limit=...`, cursor monotônico e dedupe do lado cliente.

### 6. Artifacts: JSON preservado no banco; conteúdo de arquivo não é compartilhado/durável por banco

`AgentArtifact` liga `taskId`, tipo, `summary` e `data` JSON; a task mantém array de IDs (`packages/domain/src/agent.ts:26-48,100-108`; `apps/server/src/engine/service.ts:672-691`). Essas ligações são convenções, sem FK que impeça artifact órfão ou task de outro owner. PDFs são gravados como `${DATA_DIR}/files/{id}.pdf`, e metadata fica em `records`; o link é assinado por owner no momento de leitura (`apps/server/src/files.ts:17-75`). O processo grava arquivo e metadata em operações separadas. Sem volume realmente compartilhado/backup, trocar host ou separar API/worker pode tornar o arquivo indisponível mesmo que o metadata sobreviva.


### 7. Worker tem claim condicional, mas varre todos os tasks a cada tick

`TaskWorker` inicia polling a cada segundo e chama `Store.scan("tasks")`; `scan()` consulta records de todos os owners por `kind`, depois o worker filtra status/due time em JavaScript e executa até três elegíveis (`apps/server/src/engine/worker.ts:45-52,64-112`; `apps/server/src/db.ts:71-76`). O CAS de claim evita que duas instâncias tomem o mesmo task, mas não evita cada uma carregar o conjunto inteiro. O schema não declara índice para `kind` global nem para status/due time dentro do JSON; o custo de polling e o tráfego de rows crescem com o histórico total. Manter fila durável no PostgreSQL, mas promover status/due/lease a colunas indexáveis e reivindicar lote com SQL/`SKIP LOCKED`; Realtime/`pg_notify` podem acordar o poller, nunca substituir o registro persistido.

## Modelo-alvo Supabase/Postgres/Realtime sem sacrificar recovery

1. **Migrações e base tipada.** Introduzir SQL migrations Supabase versionadas, executadas uma vez pelo pipeline/release, não por todos os processos no boot. Tabelas núcleo: `tasks`, `task_runs`, `task_events`, `actions`, `action_attempts`, `idempotency_keys`, `artifacts` e `audit_events`; `owner_id uuid` para Auth, IDs de recursos em `text` no período de compatibilidade. Use PK/unique/FK compostas `(owner_id,id)` para impedir referências entre owners. Manter snapshots/checkpoints JSONB para recuperar o agente; normalize status, due time, lease, owner e correlação em colunas tipadas. `system` fora do namespace de usuário.
2. **Claims SQL e event append na mesma transação.** Substituir scan completo por claim de tasks due em lote com `FOR UPDATE SKIP LOCKED`, `lease_until` e timestamps definidos por SQL, attempt cap e índices parciais por estado/due time. OpenBot implementa este padrão com tabela de work, idempotência em `(kind,key)`, tentativas e notificação que serve só para acordar o poller; a row PostgreSQL continua sendo a verdade [8] [9]. A referência OpenDots inclui claim, run e primeiro evento em uma transação `BEGIN IMMEDIATE`, mas é SQLite de **single-owner**, não é esquema multi-tenant para copiar diretamente [12].
3. **Eventos e outbox.** Na mesma transação que atualiza task/action, anexar evento com sequência e incluir row na `outbox`. Relay/trigger publica somente `event_id`, task e versão mínima; consumidor/UI lê `task_events` após cursor. Se o processo cair após commit e antes de notificar, outbox republica; se o cliente estiver offline, faz catch-up do banco. Manter snapshot/checkpoint para recovery do trabalho e evento append-only para replay/audit/UI. A trilha de execução e a trilha de auditoria administrativa devem compartilhar IDs de correlação, mas continuar com retenção e controle de acesso adequados ao payload.
4. **Realtime como transporte de baixa latência, não fonte da verdade.** A UI pode assinar Broadcast privado no topic da task ou alterações selecionadas. Criar policy de `realtime.messages` que verifica usuário autenticado, topic e relação task/owner; Supabase avalia policies para o topic ao conectar e exige canal privado com `config.private: true` [4]. Preferir Broadcast para novos subscriptions, pois a documentação recomenda-o sobre Postgres Changes em escala; Postgres Changes autoriza por subscriber e a própria documentação descreve limites de throughput [3] [5]. Broadcast Replay existe, mas a janela documentada é de pelo menos 72h e no máximo 4 dias, com limite de 25 mensagens; não serve como history de recovery/auditoria de longa duração [3]. Não depender de canal “always connected”: no reconnect, carregar events pela API por cursor. A auth bearer atual de Whilo é token aleatório interno, não Supabase JWT; para client Realtime requer integração de Auth/JWT e rotação/logout coerentes, antes de habilitar subscrição.
5. **RLS e grants medidos, não presumidos.** Com `owner_id` UUID alinhado a Supabase Auth, ativar RLS em cada tabela exposta, separar SELECT/INSERT/UPDATE/DELETE, limitar grants e testar `auth.uid() = owner_id` tanto em `USING` quanto em `WITH CHECK` para UPDATE. Policies de outbox, idempotency e system não devem vazar payload privilegiado a clientes. O worker precisa de caminho backend com privilégio mínimo e operação explícita para cada owner; credencial service role não pode ser apresentada como RLS-enforced [2].
6. **Backfill/rollback.** Fazer backup verificável da tabela e arquivos antes da mudança; inventariar contagem e bytes por `(owner,kind)`. Mapear owners internamente e validar registros órfãos/IDs conflitantes. Criar schema novo sem apagar `records`; converter dados em lotes idempotentes e comparar contagens/hash por owner e kind. Durante dual-write, exigir uma transação real na `Store` (hoje cada `pool.query` é independente) ou mecanismo de compatibilidade no banco; não declarar dual-write atômico se os writes não compartilham transação. Rodar em staging: shadow reads, canário, auditoria de divergências, cutover e janela de rollback com tabela legada em read-only. Só remover legado após pelo menos um ciclo completo de recovery/replay e restore testado.
7. **Teste de segurança e falha.** Reaproveitar os testes PGlite atuais para state machine/SQL compatível, mas adicionar execução contra Supabase local/PG com migrations e pgTAP: sem token, owner A/B, alteração de owner, FK cruzada, bucket, topics Realtime, delete/update de event, expirado vs lease ativo, key idem igual/diferente, duas aprovações simultâneas, restart em cada fronteira entre provider e save, outbox duplicada, reconnect por cursor, e recovery de run órfão. PGlite é ótimo para banco efêmero/local/CI, mas não testa Auth hosted, autorização de canal ou serviço Realtime [1].

## Plano priorizado (risco, valor e dependências)

- **P0 — identidade, migrations e RLS comprováveis** (risco de exposição alto; valor alto; dependências: projeto Supabase, definição Auth/UUID, mapeamento de owners e credenciais por ambiente). Antes de expor acesso client-side, escrever migrations e policies CRUD para cada tabela/bucket, testar cross-owner com tokens separados, separar system data, e demonstrar quais processos usam qual papel. Não habilitar Realtime público nem enviar service key ao cliente.
- **P0 — fechar colisão de idempotency keys e recovery de action** (risco de duplicate side effect/confusão alto; valor muito alto; dependências: IDs estáveis de invocation, request fingerprint, suporte ou reconciliação por provider). Rejeitar chave com payload diferente; expor key API; scope da recuperação a leases expirados e inserir audit event da resolução. Saída incerta segue bloqueada até reconciliação; release gate: após crash depois de enviar provider, nenhuma execução automática duplicada.
- **P1 — tabela e worker transacionais** (risco de escala/corrupção histórica alto; valor alto; dependências: migração expand/contract, adapter transacional, worker tests contra PG). Tipar tasks/runs/statuses, claim indexado com clock do banco e `SKIP LOCKED`, terminalizar runs vencidos, attempts/cap e reconciliação; persistir task transition + run + event + outbox em uma transação.
- **P1 — event/audit cursor e integridade** (risco de replay incompleto e investigação parcial médio-alto; valor alto; dependências: IDs e sequência, política de retenção, redaction). Adotar log append-only por task, associação run/action/provider receipt, API paginada por cursor e testes de queda entre operações. Manter snapshot JSON para execução; não exigir replay completo do LLM para restaurar task.
- **P1 — artifacts duráveis** (risco de perda por host médio-alto; valor alto; dependências: Storage privado, policies de objeto e backfill de PDFs). Usar bucket com path baseado em owner, object checksum, upload reconciliável e links assinados on demand; preservar metadata e mapear arquivos antigos antes de limpar volume.
- **P2 — Realtime incremental** (risco baixo após persistência/outbox; valor médio-alto para UX/custo de polling; dependências: Auth JWT, channel policies, client SDK). Só depois do cursor/outbox: trocar polling global por Broadcast privado como hint e fazer read-after-cursor/periodic resync; nunca usar janela curta de replay como garantia de entrega.

## Comparação com os upstreams oficiais

- **OpenMuse:** a versão oficial atual de `apps/server/src/db.ts` tem a mesma estrutura PGlite + `pg` e tabela genérica `records`, e o `engine/service.ts` tem o mesmo modelo de task/checkpoint/events. Assim, OpenMuse confirma que a base local é funcional e oferece padrões de recuperação, mas não é evidência de RLS, Supabase ou schema normalizado; é o mesmo ponto de partida, não uma solução de migração [10] [11].
- **OpenBot:** é uma referência útil para a etapa seguinte, não uma integração que Whilo já tem. README e arquitetura descrevem PostgreSQL para dados do produto; há schema Drizzle por domínio, trilha `audit_events` com indexes por ator/tipo/alvo e canal/membership; seu work queue faz claim transacional com `SKIP LOCKED`, clock do banco, attempts e dedupe `(kind,key)` [7] [8] [9] [10]. O próprio OpenBot trata notificações/listeners como otimização, não entrega durável; adaptar o conceito da queue/outbox, sem copiar seu authorization model como se fosse RLS.
- **OpenDots:** `src/server/store.ts` usa SQLite, com tabelas distintas para tasks/runs/events, transação imediata para claim, grava run e evento, e índice de eventos por task. O `Runner` renova lease e interrompe quando perde ownership [12] [13]. É um exemplo pequeno de atomicidade e ordenação, mas seu store não carrega `owner_id` e é single-owner; não prova multi-tenant ou Supabase.
