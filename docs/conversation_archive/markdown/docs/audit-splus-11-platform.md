# Auditoria S+ independente — plataforma e operações Whilo

**Parecer:** **ainda não é S+ para produção**. O repositório tem bons controles locais para o worker de Chromium e testes úteis, mas descreve uma aplicação que precisa de processos persistentes, estado durável e disco; não contém uma topologia de produção declarada, pipeline de publicação/rollback do backend, contrato de webhook implementado, SLOs ou operação de backup e observabilidade. Nota do eixo Cloudflare/Vercel/GitHub/ops: **4/10** — boa base de engenharia local, lacunas operacionais de alto impacto. A nota é uma avaliação estática do repositório, não uma nota do serviço atualmente em execução.

A auditoria examinou o checkout local e páginas oficiais consultadas em **3 de outubro de 2026**. Não havia configuração/acesso às contas Cloudflare, Vercel, GitHub Environments ou aos ambientes de produção. Assim, um projeto Vercel configurado no painel, DNS, WAF, secrets, backups ou deploy fora do repositório não foi presumido nem declarado inexistente; falta evidência versionada para verificá-los.

## Estado encontrado

- **Já existe — testes e limites operacionais do browser.** `apps/worker/Dockerfile:1-9` fixa a versão Playwright, instala dependências de produção, executa como `pwuser` e usa `/data` como diretório de perfil. `infra/compose.yaml:3-32` reinicia o serviço, persiste perfis em volume nomeado, publica a porta só em loopback no host, limita memória/processos e remove capacidades. A CI roda testes de Chromium e de containers (`.github/workflows/ci.yml:51-91`). Isso é uma boa base para um serviço privado, não uma configuração de produção HA.
- **Parcial — Vercel é apenas o build da interface estática.** `vercel.json:1-7` declara `pnpm build:web` e `apps/mobile/dist/web` como diretório publicado. O bundle lê `EXPO_PUBLIC_API_URL` no cliente (`apps/mobile/src/api.ts:3-6`); essa variável precisa apontar para um endpoint público HTTPS no momento do build, e não deve conter segredo. O arquivo não define a API, o worker de tarefas, o browser, filas, domínios, regras de rewrite para a API ou observabilidade. A configuração do diretório determina o que Vercel serve como estático; não implica que a aplicação Hono tenha sido implantada como função [1].
- **Parcial — API e worker de tarefas são processos Node, com estado local por padrão.** `apps/server/src/index.ts:6-15` cria o store e, por padrão, inicia `agent` e o scheduler no próprio processo HTTP. O README admite worker separado, mas exige `DATABASE_URL` e os mesmos secrets/`DATA_DIR`; afirma expressamente que PGlite não pode ser aberto por processos separados e que se deve rodar uma instância da API (`README.md:130-136`, `.env.example:29-31`). `apps/server/src/worker-entry.ts:5-13` confirma a exigência de PostgreSQL para o worker separado. O código não fornece um Dockerfile nem manifest de deploy da API. Portanto, a instalação Docker existente não entrega o backend completo.
- **Parcial — já há execução durável via SQL, mas não um broker externo ou outbox.** `apps/server/src/engine/worker.ts:45-52,64-111,116-182` varre tarefas, tenta no máximo três tarefas elegíveis por tick, usa compare-and-swap/lease com heartbeat e polling de um segundo. A tabela SQL é hoje a fonte da verdade dos trabalhos. Isso oferece recuperação e coordenação por lease, mas o scan cresce com o conjunto de tarefas e não equivale a Cloudflare Queues, DLQ, métricas de backlog ou uma política de reentrega administrável. Não se deve trocar a tabela de tarefas por mensagens transitórias sem preservar idempotência, estados e recuperação.
- **Ausente — webhook de produto operacional.** `apps/server/src/o1/routines.ts` modela um trigger `webhook` com chave e `apps/server/src/app.ts:289-296` permite criar rotinas desse tipo; porém a rota de eventos existente é `POST /api/o1/events` (`app.ts:219-223`), atrás do middleware de autenticação de owner (`app.ts:144-149`), e `O1EventRouter` somente faz match de triggers `type === "event"` (`apps/server/src/o1/event-router.ts:25-37`). A busca no código não encontrou rota pública de recepção, validação de assinatura, timestamp/replay nem handler de rotina webhook. Os registros chamados `queued` são gravados e despachados sincronicamente por `O1RoutineDispatcher` (`apps/server/src/o1/routine-dispatcher.ts:10-27`), não consumidos por um broker independente. Há uma referência de uso de `stripe listen` em `apps/server/src/o1/payments.ts`, mas isso não constitui por si só um endpoint de webhook.
- **Parcial — health check não expressa prontidão operacional.** O endpoint da API reporta `ok: true` e configuração booleana (`apps/server/src/app.ts:150-157`), sem testar uma consulta ao banco ou disponibilidade real do worker. O worker expõe `/health` sem autenticação e retorna apenas `status: ok` (`apps/worker/src/server.ts:50-55`); o próprio manual diz que não confirma que Chromium inicia (`apps/worker/README.md:23,47`). O healthcheck do Compose usa esse endpoint (`infra/compose.yaml:25-29`). Não há readiness separada nem probes sintéticos fim a fim no repositório.
- **Parcial — segurança de CI boa; entrega de software ausente no workflow versionado.** `.github/workflows/ci.yml:7-30` restringe `GITHUB_TOKEN` a `contents: read`, desliga `persist-credentials` e fixa actions por SHA; faz lint, typecheck, testes e build. Também verifica exports de UI e containers. Contudo, o único workflow existente é CI: não publica imagens versionadas/digest, não implanta preview ou produção, não executa smoke test pós-deploy, não promove releases nem define aprovação/rollback. A configuração de Vercel pode existir fora do Git, mas não está documentada neste checkout. GitHub recomenda mínimo privilégio, pin de actions por SHA e controle de secrets/environment [2][3].
- **Ausente — SLO, retenção de logs, alertas e recuperação de dados.** `apps/server/src/log.ts` e os logs do processo não formam uma estratégia operacional versionada: não há exporter/tracing/metrics, alertas, política documentada de retenção, backup/PITR verificado ou exercício de restore. `DATA_DIR` guarda estado que inclui banco PGlite, documentos e chave de assinatura de sessão (`README.md:130-134`; `apps/server/src/auth.ts:73-83`). `WORKER_DATA_DIR` guarda cookies/perfis e PDFs (`apps/worker/README.md:49-58`). Um redeploy, host substituído ou volume perdido pode causar perda ou indisponibilidade desse estado se a plataforma não mantiver esses diretórios.

## Topologia S+ proposta

```text
Web / iOS / Android
  └─ Web: Vercel publica somente o Expo export estático
       EXPO_PUBLIC_API_URL=https://api.whilo.example (configuração pública por ambiente)

api.whilo.example
  └─ Cloudflare DNS + proxy/WAF + limites de requisição + TLS
       └─ Edge gateway leve: identificação/correlation ID, regras de entrada e roteamento;
          não executa o loop de tarefas nem Chromium
            └─ origem Node/Hono privada (serviço containerizado, sempre ligado)
                 ├─ PostgreSQL gerenciado (backups/PITR, rede privada, pooler)
                 ├─ Object storage privado para PDFs/artifacts, com URLs curtas assinadas
                 ├─ provider/Intelligence APIs (credenciais exclusivamente server-side)
                 ├─ browser-worker privado, em pool/partições com volumes duráveis
                 └─ computer gateway/container isolado, opcional, separado do host da API

Webhook externo
  └─ Cloudflare Worker ingress (validar assinatura e limites; segredo do provider)
       └─ Cloudflare Queue / retry + DLQ
            └─ consumidor persistente Node: inbox/outbox no PostgreSQL,
               deduplicação por provider/event ID e criação de task idempotente
```

**Cloudflare:** tratar Workers como camada de entrada e glue de baixa latência, não como runtime da aplicação. Os limites publicados incluem 128 MB por isolate e CPU até cinco minutos no plano pago, mesmo que a duração wall-clock de uma requisição HTTP não tenha limite declarado. Isso não equivale a processo persistente que faz polling, mantém estado local, abre browser e executa trabalho sem limite; consumidores de Queue também têm limites próprios [4]. Use regras WAF/rate limiting para reduzir abuso de rotas públicas, login e ingress; os contadores Cloudflare podem levar alguns segundos para refletir a taxa e não substituem rate limit por owner/idempotência na aplicação [5]. Manter a origem acessível somente via caminho Cloudflare/Tunnel ou allowlist equivalente, e worker/browser APIs em rede privada. Não transformar o segredo de acesso da origem em uma variável pública do Expo.

**Vercel:** manter a interface estática e previews de PR, com `EXPO_PUBLIC_API_URL` separado entre preview/staging e produção. Confirmar no projeto o diretório raiz, build command, output e variáveis do projeto; não inserir `CPK_INTELLIGENCE_API_KEY`, chaves de provider, `TOKEN_ENCRYPTION_KEY`, `WORKER_TOKEN` ou credenciais de banco no Vercel client bundle. Uma variável alterada só afeta novos deployments [6]. Vercel Functions têm duração limitada — hoje 300 s no Hobby e até 800 s no Pro/Enterprise, com 1.800 s em beta sob condições; existe Vercel Workflows para workflows de minutos a meses, mas isso seria uma implementação nova, não uma propriedade do `vercel.json` atual [7]. O serviço persistente descrito no README não deve ser confundido com uma função HTTP.

**API e workers:** containerizar API e `start:worker` como serviços Node independentes e sempre ligados, no mesmo domínio de rede/região do PostgreSQL. Em produção, usar `DATABASE_URL` para ambos e desligar `TASK_WORKER_ENABLED` na API quando houver worker separado. Migrar arquivos locais e a chave de assinatura de sessão para armazenamento durável/seguro compartilhado antes de separar processos em hosts distintos; a instrução atual de `DATA_DIR` compartilhado não fornece por si só um armazenamento compartilhado seguro. Aplicar migrations como job de release serializado, não simultaneamente no boot de réplicas. Adotar database connection pooling considerando o pool de até cinco conexões por processo (`apps/server/src/db.ts:115-128`). O browser deve continuar serviço privado; se escalar, gravar afinidade `sessionId → worker/volume` e mover/reanexar a sessão conscientemente, ou manter shard persistente por volume. Clonar réplicas sem afinidade não garante que um screenshot/navigate chegue ao perfil que possui cookies.

**Fila e webhooks:** preservar PostgreSQL como fonte de verdade de tarefa/estado/lease. Adicionar `webhook_inbox` com unicidade por `(provider, event_id)` e uma transactional outbox na mesma transação que cria a tarefa. Um relay publica apenas IDs/envelopes mínimos para Cloudflare Queues; consumidor Node busca payload autorizado no banco, adquire a lease SQL e só confirma a mensagem depois de gravar o recebimento/idempotência. Mensagens de Queue podem ser reentregues e precisam ser idempotentes; configure retry/backoff e uma DLQ desde o primeiro consumidor, pois ao atingir `max_retries` sem DLQ a mensagem pode ser apagada [8][9]. Cloudflare documenta pull consumers via HTTP para clientes externos, com lease/visibility timeout; isso é compatível com um serviço Node externo, mas exige credencial de API do Queue, ack/retry e timeout maior que a janela de trabalho ou uma estratégia de claim bem definida [10]. Não envie prompt completo, token ou corpo sensível de provider ao broker se um ID e referência de inbox forem suficientes. Para cada webhook, verificar assinatura sobre o body original, janela temporal/replay, rotação de chave, limite de tamanho, allowlist de eventos e provider event ID; responder 2xx somente após persistência durável. O endpoint atual autenticado de eventos permanece apropriado para chamadas internas, não como substituto desses contratos.

**Secrets:** manter classes separadas. `CPK_INTELLIGENCE_API_KEY`, chaves de modelo/OAuth, credenciais de banco, `TOKEN_ENCRYPTION_KEY` e browser/computer service tokens pertencem ao runtime de servidor/segredo gerenciado; segredo de validação do provider só ao ingress que o necessita. `WORKER_TOKEN` atual é um segredo estático compartilhado, documentado tanto para API quanto browser (`.env.example:33-37`); rotacionar por serviço/ambiente e reduzir privilégio/raio de impacto. Vercel só recebe valores que aquela função/build efetivamente necessita. Secrets de Cloudflare Worker são bindings secretos, não vars públicas. GitHub mantém apenas credenciais de deploy inevitáveis em environment protegido; a documentação de Workers exige `CLOUDFLARE_API_TOKEN` e `CLOUDFLARE_ACCOUNT_ID` no CI, recomenda token escopado ao account/zone, e não declara OIDC para esse fluxo [11][12]. Usar OIDC/credenciais curtas onde o provedor de runtime realmente o suporta, sem assumir suporte universal; aplicar environment `production` com branch allowlist, reviewer e self-review bloqueado [3][13].

## SLOs propostos e medição

Estes são **alvos iniciais**, não medições do sistema atual. Medir por 28 dias em staging/prod antes de prometer contrato externo; excluir latência de LLM/provider do SLO de API síncrona e publicar sua disponibilidade separadamente.

- **API síncrona:** disponibilidade mensal de 99,9%; `p95 < 300 ms` em rotas sem inferência/modelo. Monitor sintético externo consulta health/readiness e executa autenticação/leitura leve.
- **Recepção e despacho:** 99,9% dos webhooks válidos persistidos antes do 2xx; `p95 < 10 s` da aceitação até o worker iniciar a tarefa; nenhum evento inbox sem estado final/alerta por mais de cinco minutos. Alertar sobre backlog idade, taxa de DLQ, lease expirado e maior idade de tarefa `queued`.
- **Browser service:** 99,5% de sucesso em checks sintéticos de criar sessão, navegar em fixture pública e capturar imagem; distinguir processo vivo de Chromium utilizável e medir limites/erros de memória e fila de sessão.
- **Dados e recovery:** objetivo de RPO ≤ 5 minutos e RTO ≤ 60 minutos condicionado a PostgreSQL com PITR/backup, storage de artifacts replicado, runbook e restore testado. O repositório não demonstra hoje nenhum desses valores.
- **Release:** rollback do frontend ou API/container em até dez minutos a um artefato conhecido, com cada build associado a commit, tag e digest; nenhuma migration destrutiva no mesmo release que ainda pode exigir rollback de app.

Instrumentar logs JSON sem access keys, tokens, cookies, prompt completo ou conteúdo documental; associar `request_id`, `task_id`, `run_id`, `routine_id` e `provider_event_id` não secreto entre Cloudflare, API e worker. Exportar métricas de request/error/latência, DB pool/erro, backlog por idade/estado, leases, tentativas, DLQ, worker health e gasto externo. Cloudflare fornece logs, traces, métricas de invocação e export OpenTelemetry para o edge, mas isso não instrumenta automaticamente o runtime Node/API [14].

## Publicação, rollback e operação

1. Separar CI de deploy. Em PR: instalar lockfile, lint/typecheck/teste, teste de Chromium, build server e browser/computer images, dependency review/scan e smoke; para imagem, gerar SBOM, escanear e guardar digest/proveniência. O workflow atual já fixa actions por SHA e usa permissão de leitura, o que deve ser preservado.
2. Em merge/commit aprovado, buildar uma vez e publicar imagens imutáveis API/worker/browser no registry; implantar staging, rodar migrações compatíveis e smoke de `/api/health`, readiness DB, fila, browser privado e caminho principal fake; depois solicitar aprovação do GitHub Environment `production`. Nunca expor credenciais de produção em jobs de PR/fork. Implantar edge Worker separadamente com `wrangler` e credentials scoped; a documentação Cloudflare ilustra token e account ID, não token amplo de conta [11].
3. Para Vercel, usar integração GitHub para previews e deploy conforme branch de produção se esta for a configuração escolhida; exigir check de CI e testar o `EXPO_PUBLIC_API_URL` do preview. A integração cria deployment por push e previews em PR, mas a existência dela no dashboard não pode ser afirmada a partir do repositório [15].
4. Após canário, verificar health/readiness, erros 5xx, login/API sintética e início de tarefa antes de aumentar tráfego. Health atual sempre positivo não deve ser o gate de promoção.
5. **Rollback da UI:** reverter/rollback para deployment Vercel anterior; o comando aponta produção para deployment já construído, mas a disponibilidade de alvo antigo depende do plano. Isso restaura somente o frontend e configuração daquela versão, não banco, browser volume ou API [16].
6. **Rollback do backend:** redeploy do último digest bom, com rollout gradual e sem `latest`. Para migration, aplicar expand → deploy compatível → backfill → contract em release posterior. Não “desfazer” migration destrutiva com rollback cego: restaurar backup/PITR só por procedimento de incidente aprovado, com avaliação de perda de escrita desde o snapshot.
7. Registrar runbooks para perda de DB, volume de browser, Queue/DLQ, segredo vazado, deploy com erro, indisponibilidade de CopilotKit/provider e restart preso. Exercitar mensalmente restore e trimestralmente rollback/rotação; registrar owner de on-call e critério de escalonamento.

## Referências comparativas: OpenBot, OpenMuse e OpenDots

- **OpenBot** documenta uma distribuição que pode levar UI/API/Chromium em um container com PostgreSQL embutido opcional e volume persistente; sua própria documentação exige usar digest em vez de tag móvel para releases e recomenda migração externa em etapa separada antes de servir com múltiplas réplicas. O supervisor de computadores não está dentro da imagem; sem ele os Bots compartilham browser, estado e logins. É referência de packaging/self-hosting, não prova de isolamento entre tenants nem de que Whilo possa executar esse desenho sem integração [17].
- **OpenMuse** publica um exemplo Render com três serviços: API Node com `/api/health` e disco de dados, site web estático e browser private service com disco/token. O API executa o task worker in-process no blueprint e API precisa manter `DATA_DIR` no disco; o próprio README diz que o host precisa permanecer ligado para background work. É um exemplo concreto de separação dos serviços que existem neste repo, mas não fornece automaticamente HA, backup testado, SLO ou política multi-região [18].
- **OpenDots** conecta cada specialist a um computador OpenBot, com volume por Dot, rede de controle separada e Docker socket somente no supervisor. Seus docs avisam que o socket não chega à app nem aos computadores, que as ações ainda compartilham o kernel do host, e que é preciso operação de volumes/containers dinâmicos além do Compose. É um bom padrão de isolamento do computer plane; o `apps/computer` local deste projeto, explicitamente single-owner em `SECURITY.md:15-25`, não deve ser promovido a supervisor multi-tenant sem adoção e verificação dessa fronteira [19].

## Plano de implementação priorizado

- **P0 — definir a origem e persistência de produção (alto risco/alto valor).** Criar deployment manifest/container para API, worker e browser; decidir host Node always-on; tornar PostgreSQL gerenciado obrigatório para processo separado e réplicas; migrar arquivos/chave de sessão para storage durável seguro; executar backup e teste real de restore. Dependências: domínio/API, provider de runtime/database/storage, orçamento e retenção.
- **P0 — completar gate de deploy.** Adicionar workflow de release/build por digest, staging, smoke, environment production protegido e rollback documentado. Separar Vercel static build da publicação de serviços backend. Dependências: permissões de registry, Cloudflare token escopado, ambiente Vercel/branch e owners/reviewers.
- **P0 — readiness, telemetria e SLO.** Implementar readiness que verifica banco e configuração operacional crítica sem vazar segredo; browser check que confirma launch Chromium; correlation IDs, métricas, alertas e dashboards; medir baseline antes de afirmar metas. Dependências: stack de observabilidade/on-call e política de privacidade/retention.
- **P1 — webhook inbox/outbox e fila segura.** Implementar rota real com assinatura/replay/dedupe, persistir o inbox/outbox em transação e conectar Queue com DLQ/replay e consumer idempotente; não confundir trigger schema com endpoint. Dependências: fornecedores de webhook, esquema de eventos, secret store, Cloudflare Queue e runbook.
- **P1 — borda e segmentação de segredo/rede.** Configurar Cloudflare WAF/rate-limit/TLS e proteção do origin; manter Vercel como static-only; permitir browser worker apenas da API; segmentar/rotacionar tokens; definir permissões de preview versus prod. Dependências: domínio e planos/recursos Cloudflare aplicáveis; as capacidades de regras de rate limit variam por plano [5].
- **P2 — escalar com afinidade e rollout progressivo.** Remover o scan integral da fila sob crescimento ou indexar/claimar só tarefas elegíveis; confirmar `FOR UPDATE SKIP LOCKED`/lease concorrente para o banco escolhido, controlar pool de conexões, testar partição/afinidade de browser sessions, autoscaling por backlog e canary progressivo. Dependências: volume/backlog real, índices/migração, capacidade do plano e benchmark de browser.

**Evitar:** executar API/task loop/Chromium persistente como Vercel Function ou Cloudflare Worker; presumir que o output estático do `vercel.json` publicou backend; pôr secrets de runtime no `EXPO_PUBLIC_*`; expor browser/computer service publicamente; escalar PGlite/local disk em vários processos; confiar no simples `/health` como readiness; introduzir Cloudflare Queues sem deduplication, DLQ e inbox/outbox; usar tags Docker móveis em produção; e interpretar rollback de frontend como rollback de dados/API.
