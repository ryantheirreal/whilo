# Auditoria S+ 04 — browser, computador e takeover

**Veredicto:** Whilo tem uma base local de computador bem isolada e um browser worker seguro para navegação pública, mas ainda não entrega um fabric unificado nem takeover humano confiável de ponta a ponta. O adapter OpenBot está desativado e não compatível com o protocolo de takeover do submódulo atual. **Não habilitar OpenBot para tráfego de produção antes de reconciliar o contrato e fechar o bloqueio de ações durante takeover.**

**Score do eixo: 5/10** — isolamento e filesystem local: 7/10; integração do fabric e takeover: 3/10. A análise é estática do código/configuração local e das fontes oficiais consultadas em 2026-10-03; não houve verificação de um deployment Whilo/OpenBot ativo. Nenhum código de produção foi modificado.

## Estado por capacidade

### Fabric e lifecycle de computadores — **parcial; alto risco de integração**

A trilha Docker local é concreta: cria um container por proprietário, com usuário `1000:1000`, root filesystem somente leitura, sem capabilities, rede Docker `none`, limites de CPU/memória/PIDs e um volume persistente `/workspace`; antes de reconectar, inspeciona a configuração e recusa containers incompatíveis (`apps/server/src/computer.ts:113-138,225-318,441-511`; `docs/COMPUTER.md:48-54`). Isso é uma boa barreira de isolamento para um produto single-owner, mas é container compartilhando kernel, não VM nem garantia contra tenants hostis (`docs/COMPUTER.md:54`).

A abstração O1 de provider/lifecycle é **um seam, não um fabric pronto**: `ComputerProvider` declara create/get/start/stop/destroy (`apps/server/src/o1/computer-provider.ts:1-17`); `HetznerComputerProvider.create()` apenas faz `POST /servers`, devolve o ID/IP e não instala daemon, agente, volume/workspace ou egress policy (`apps/server/src/o1/hetzner-computer-provider.ts:11-66`). O ID/IP retornado não é ligado ao `HttpComputerGateway`: o gateway usa um `baseUrl` único e só envia `computerId` em rotas genéricas (`apps/server/src/o1/computer-gateway.ts:30-52`), enquanto a sessão persiste `providerId` e descarta o endpoint (`apps/server/src/o1/computer-sessions.ts:8-17,36-46`). Não há aqui protocolo de bootstrap/reconciliação para tornar a VM utilizável. Um timeout de provisionamento pode deixar infraestrutura criada sem registro local; não há chave de idempotência ou reconciliação no contrato de `create`.

`createComputerFabric()` cria um `persistentGateway` apenas se URL e token estiverem configurados e um `BrowserWorkerGateway` separado (`apps/server/src/o1/computer-fabric.ts:7-34`). O app liga somente provider + gateway persistentes a `O1ComputerSessionService` (`apps/server/src/app.ts:76-89`); os endpoints O1 de execução usam `persistentGateway` (`apps/server/src/app.ts:227-257,312-383`). O caminho `browserGateway` não é passado à sessão nem ao CUA runner; o browser utilizável pela conversa é outro serviço (`BrowserService`). O `COMPUTER_ENABLED` Docker local e esse fabric remoto são trilhas distintas, sem lifecycle unificado.

A identidade também não está decidida entre os modelos: o container Whilo é por `owner` (`computerIdentity`, `apps/server/src/computer.ts:113-125`); a sessão O1 não armazena `agentId`/`botId` (`apps/server/src/o1/computer-sessions.ts:8-17`); OpenBot/OpenDots modelam computador por Bot/Dot [1] [9] [10]. Para um produto multi-coworker, esse compartilhamento pode expor arquivos, logins e estado de browser entre agentes do mesmo proprietário. Ou documentar explicitamente um computador pessoal compartilhado e controlar grants por agente, ou particionar por `(owner, agentId)`.

### Browser worker e screenshots — **existente para navegação pública; parcial como computador**

O worker Playwright aceita URL pública, navegação, leitura de texto, screenshots PNG 1280×800, input por coordenadas/teclado e importação controlada de PDFs; mantém perfis e fecha sessões ociosas (`apps/worker/README.md:17-57`; `apps/worker/src/browser.ts:36-57,113-135,152-224,284-389`). O token fica entre API e worker, não no cliente; a validação DNS/IP restringe destinos a HTTP(S) público nas portas 80/443 e bloqueia destinos privados (`apps/worker/README.md:60-64`; `apps/worker/src/network.ts:46-95`). Esse caminho é valioso e deve permanecer distinto do computador com shell: não executa filesystem/shell, desativa WebSockets e service workers, fecha popups/diálogos e não promete compatibilidade com qualquer aplicação web.

A tela humana atual é um console de screenshots: recarrega a imagem a cada 2 segundos e envia click/text/key/scroll por HTTP (`apps/server/src/browser-console.ts:14-37`). A screenshot pode ser vista em web/native via iframe/WebView (`apps/mobile/src/BrowserConsole.web.tsx:1-9`; `BrowserConsole.native.tsx:5-16`). **Não existe screencast WebSocket/WebRTC ligado ao BrowserService**; a tela de vídeo e o gateway de stream do OpenBot são outro protocolo [2] [3]. O `BrowserWorkerGateway` converte ações e lê texto/screenshot, mas explicitamente recusa shell (`apps/server/src/o1/browser-worker-gateway.ts:21-48`).

### Filesystem e shell — **existente no Docker local; parcial no fabric**

O filesystem `/workspace` impõe limites de caminho e tamanho; o helper Python abre diretórios/arquivos com `O_NOFOLLOW`, restringe a `/workspace`, rejeita arquivos especiais e troca arquivo escrito atomicamente (`apps/computer/files.py:9-35,46-90`). O shell é um comando não interativo via `docker exec`, com `30s` e saída combinada até 128 KiB; timeout/interrupção grava recibo e tenta parar o container, mantendo-o bloqueado se não consegue confirmar o stop (`apps/server/src/computer.ts:15-17,591-750`). PDF é o único fluxo de bytes suportado; leitura/escrita de texto limita-se a 256 KiB (`apps/server/src/computer.ts:15-16,752-823`). A rede está deliberadamente desativada para o shell, logo não se deve anunciar instalação/download de pacotes como OpenBot faz; habilitar rede exigiria egress proxy/ACL, não só remover `--network none` (`apps/server/src/computer.ts:465-508`; contraste: [1] [2]).

O acesso de agente passa por `computerTools()` e pelo modo `ask_o1` por padrão para writes (`apps/server/src/computer-tools.ts:12,15-44,67-120`; `apps/server/src/o1/permissions.ts:9-47`). Porém o contrato direto de ComputerService é por proprietário, não por agente/initiator, e seus comandos/arquivos ficam em recibos mutáveis próprios, não necessariamente no audit ledger append-only. O browser console também chama `BrowserService.input()` diretamente. Antes de tornar isso multi-agente, unificar identidade, grant e auditoria por operação; não usar o mero login do proprietário como substituto de permissão do coworker.

### OpenBot computer protocol — **adapter parcial e driftado**

O adapter server-side existe e está desligado por padrão (`packages/backends/src/openbot.ts:3-14,99-118`). Expõe probe, criação de conversa, status, snapshot, navigate e endpoints de controle; não implementa click/type/key/scroll, screenshot, files/list/read/write, shell, download nem stream. Sua própria documentação chama filesystem e interação completa de extensões futuras (`docs/OPENBOT-INTEGRATION.md:55-70`). Portanto “suporte OpenBot” não deve ser apresentado como computador funcional.

Há um **mismatch executável de takeover**. O adapter declara `OPENBOT_CONTRACT_REF=a96d88c6…` (`packages/backends/src/openbot.ts:3-4`), mas o gitlink local `openbot` está em `cb5dc32a…` (tag v0.1.0, 2026-10-02); a integração documentada ainda diz que foi inspecionada em 15/09 na revisão `a96d88c6` (`docs/OPENBOT-INTEGRATION.md:3,57-70`). No protocolo presente, `ComputerControlState` traz o objeto de solicitação e identidade do handoff (`openbot/shared/computer-control.ts:14-36`); a rota `/control/request` devolve esse estado, e take/release chamam `handoffId(body)` (`openbot/server/src/computer/routes.ts:351-375,436-451`). O adapter não modela `request`/`requestId` em `controlSchema` (`packages/backends/src/openbot.ts:53-60`) e `takeControl()`/`releaseControl()` enviam body vazio (`:227-243`), então perde a identidade necessária e não consegue completar a transição. Os testes atuais chamam take/release sem `requestId` contra um mock que devolve estado sem solicitação; verificam rota/método, mas não validam a transição no server real (`tests/openbot.test.ts:25,197-213`).

Além disso, `unsupportedCapabilities` omite files/shell apesar de não existirem métodos (`packages/backends/src/openbot.ts:104-110`). Não há configuração OpenBot no `Config` nem instância do adapter em `createO1Platform()` (`apps/server/src/config.ts:45-57,132-144`; `apps/server/src/o1/index.ts:12-35`). A documentação local já reconhece que não há bridge de sessão nem round trip ativo (`docs/OPENBOT-INTEGRATION.md:74-76`). O contrato público OpenBot é um projeto alpha/template, não pacote estável: fixar commit e validar contra o server pinado, não contra mocks ou `main` flutuante [1] [8].

### Takeover — **parcial e de alto risco**

A experiência Whilo permite que uma pessoa clique/digite no browser atual, mas não implementa takeover com exclusividade. O console manda inputs para `POST /api/browsers/:id/console`, que chama `browser.input()` sem `control`/lease (`apps/server/src/app.ts:697-707`; `apps/server/src/browser.ts:225-233`). O browser worker serializa a fila por sessão (`apps/worker/src/browser.ts:43-46,65-74`), e o serviço também serializa por sessão em memória (`apps/server/src/browser.ts:34,57-64`), mas serializar não significa pausar/refusar o agente: as ações humanas e do Bot podem ambas ser aplicadas em sequência, e o map não é lock distribuído. O console não solicita, toma, libera ou expira controle; o browser agent continua habilitado enquanto a pessoa está digitando. A tela afirma “You’re controlling the agent’s browser” (`apps/server/src/browser-console.ts:18`) sem o contrato de exclusividade correspondente.

Também há caminhos de auditoria diferentes: `browser_input` do agente usa `O1BrowserActionService` e audit ledger (`apps/server/src/engine/conversation.ts:203-228`; `apps/server/src/o1/browser-actions.ts:27-49`), mas o input do console vai direto ao browser e não passa por esse serviço. O handoff O1 (`apps/server/src/o1/agent-handoff.ts:4-39`; `apps/server/src/app.ts:267-275`) registra transições genéricas de missão entre pessoa/agente; não controla BrowserService nem pausa/reata um run. A capability `human-takeover` é anunciada como S+ (`apps/server/src/o1/capabilities.ts:39`), mas a integração real ainda não cumpre esse comportamento.

O protocolo OpenBot oferece contrato melhor a adotar: solicitação identificada e durável; `take` fecha a barreira e drena ações em voo antes de conceder controle; ações do Bot são recusadas, não enfileiradas; `release` exige novo snapshot; restart marca interrupção e demanda recuperação (`openbot/agent-computer/src/control.ts:31-36,166-189,252-299,322-335`; `openbot/agent-computer/src/action-barrier.ts:1-47`). O guard central atual cobre `/exec` e `/files/write` além das mutações do browser (`openbot/agent-computer/src/authorisation.ts:55-86`; `index.ts:686-699`). Isso importa: o issue upstream #246 documentou que shell e writes continuavam durante takeover e foi fechado via PR #247; o código atual centralizou o gate depois dessa falha [5]. Ler/listar arquivos pode continuar permitidos se for decisão explícita, não como efeito acidental.

### Resultado incerto e idempotência — **parcial; bloqueador para ações de efeito**

Há bons blocos: `O1ComputerSessionService.act()` grava receipt/hash, reutiliza sucesso e recusa `outcome_unknown`/`executing` (`apps/server/src/o1/computer-sessions.ts:73-108`); `O1ComputerUseRun` tem estado `outcome_unknown`, e a rota marca incerteza se o runner lança (`apps/server/src/app.ts:312-353`); Docker command timeout/interruption é recuperado com mensagem para inspecionar arquivos antes de repetir (`apps/server/src/computer.ts:387-408,676-747`). `OpenBotAdapter.json()` também marca mutações como incertas após falha de transporte, HTTP 408/5xx ou resposta incompatível (`packages/backends/src/openbot.ts:256-314`). São contratos a preservar.

O caminho browser ainda pode repetir uma ação efetivada sem resposta. `BrowserService.request()` captura timeout/erro de transporte e troca-o por `AppError` genérico (`apps/server/src/browser.ts:66-99`), enquanto `O1BrowserActionService` só reconhece nomes `AbortError`/`TimeoutError` (`apps/server/src/o1/browser-actions.ts:19-21`); esse timeout passa a `failed`, não `outcome_unknown`, e `failed` não bloqueia uma nova execução (`:30-48`). Além disso, claim é `get` seguido de `put`, sem insert/CAS atômico (`:29-39`), e o teste cobre apenas replay sequencial de sucesso (`apps/server/src/o1/browser-actions.test.ts:17-23`). Um clique que submete pagamento/formulário pode ter sido processado mesmo quando a conexão expira; o retry do mesmo `operationId` pode clicar de novo.

Os gateways O1 remoto não impõem timeout, propagação de `AbortSignal` ou chave de idempotência no transporte (`apps/server/src/o1/computer-gateway.ts:30-52`; `browser-worker-gateway.ts:3-17,31-48`). Já o BrowserService usa timeout, mas destrói a distinção entre “não despachado” e “despachado, resposta perdida”. Ações humanas do browser console nem têm `operationId` ou recibo. Criar estados distintos `not_dispatched`, `executing`, `succeeded`, `failed_pre_dispatch`, `outcome_unknown`, `reconciled`; adquirir receipt atomicamente; após dispatch, não repetir cegamente. A chave deve identificar `(owner, agent, computer, run, action)`, e não apenas uma sequência livre do cliente.

## Recomendações implementáveis, priorizadas

1. **P0 — bloquear habilitação do adapter** até alinhar gitlink, `OPENBOT_CONTRACT_REF`, documentação e testes a um commit exato. Testar requests contra fixture do server pinado, incluindo `requestId` de ponta a ponta; `controlSchema` deve reter a solicitação e take/release/cancel devem enviar seu ID. Cobrir incompatibilidade de schema como “unknown”, nunca como sucesso. Valor: evita takeover quebrado. Dependências: decisão/pin OpenBot e fixture versionada.
2. **P0 — takeover real antes de chamar o console de takeover.** Implementar lease/control state server-side ou delegar ao OpenBot; `request → take → input → release` com `requestId`, drain do que já começou, recusa de toda nova mutação Bot (browser, shell, file-write) enquanto humano dirige, input humano admitido só com lease, TTL/restart como `interrupted`, e snapshot fresco antes do Bot retomar. Integrar Activity/audit e pausa/resume do run. Valor: reduz risco de dupla condução de ações externas. Dependências: identidade owner/agent/run, backend de controle durável e UI web/native.
3. **P1 — decidir e impor o escopo de computador.** Introduzir vínculo `(ownerId, agentId/botId, computerId, providerId)` e autorização em todos os endpoints, ou declarar que o espaço é compartilhado pelo proprietário e impedir grants/coworkers incompatíveis. Manter computer ID, Bot/agent ID, channel/thread/run/action ID distintos. Valor: evita vazamento lateral de cookies/arquivos. Dependências: roster/autorização e schema/migração.
4. **P1 — completar o fabric sem confundir worker com desktop.** Implementar `OpenBotComputerProvider`/gateway compatíveis ou um provisioner Whilo real: bootstrap seguro, armazenamento de referências de segredo (não bearer em app), mapeamento endpoint por computer, lifecycle/reconciliação e métricas; ligar `browserGateway` se realmente for suporte e reportar `ready` apenas após probe funcional. Remover ou rotular `Hetzner` como provisionamento experimental enquanto não instala runtime e agente. Valor: computadores são executáveis após create/start. Dependências: escolha de backend (OpenBot, Docker supervisor, VM), identidade e rede/egress.
5. **P1 — normalizar a fronteira de política e auditoria.** Uma ação broker server-side deve decidir e gravar antes de chamar o backend; gravar resultado/falha depois. Incluir ator, initiator (`person`, `routine`, `handoff`), Bot, computador, ação, alvo/path e receipt. Incluir inputs humanos e API direta de files/shell, não só ferramentas do modelo. Manter falha fechada. **Não copiar** o `allow: ["true"]` de startup documentado no OpenBot; exigir política de produção explícita [2]. Valor: trilha confiável e controles per-agent. Dependências: O1AuditLedger, identidade e autorização por capability.
6. **P1 — receipts atômicos e reconciliação de incerteza.** Fazer CAS/`insertIfAbsent` antes de dispatch; passar `operationId` e correlation ID até o computador; aplicar timeout com abort propagado sem converter erro pós-dispatch em “falhou com certeza”; bloquear retries após `outcome_unknown`; fornecer observação/screenshot atual e ação humana de reconciliação. Fazer o mesmo com create cloud para recuperar órfãos. Valor: evita efeitos duplicados e recursos cobrados órfãos. Dependências: DB atômico, contrato idempotente do worker e estado de run.
7. **P2 — manter browser worker como leitor/interação pública restrita; adotar stream de tela só se houver requisito.** Se o browser console atual permanecer, acrescente lock equivalente ao takeover; se for unificado com OpenBot, use seu stream autenticado e proxyado. Não encaminhar computer token, supervisor URL ou URL VNC bearer ao cliente sem proteção e ciclo de revogação. Valor: sessão responsiva e explícita; dependências: proxy de WebSocket/stream, autenticação e limites de sessão.
8. **P2 — decidir se é necessário desktop gráfico.** Whilo atual documenta corretamente que Docker não é desktop gráfico (`docs/COMPUTER.md:46-54`). OpenMuse `main` agora descreve E2B Desktop opcional, stream, screenshots e `use_desktop`; é referência possível, não funcionalidade de Whilo [6] [7]. Se adotado, tratar URL de stream como bearer secret e VNC como poder total de teclado/mouse; separar permissão desktop de browser/files/shell e testar pausa/expiração. Dependências: provedor/custo, lifecycle, URL assinada, renderer web e caminho mobile.
9. **P1 — contract/regression suite antes de S+.** Testar dois owners e dois agents; paths privados/redirects; browser login persistente; request/take/release e timeout; restart no meio do takeover; stale snapshot; não haver clique/navegação/shell/file-write sob controle humano; write e CUA com resposta perdida; dois requests simultâneos com mesmo `operationId`; logs sem conteúdo secreto. Os testes atuais de browser/O1 são essencialmente fixtures sequenciais, não integração com compute real (`tests/openbot.test.ts:197-245`; `apps/server/src/o1/browser-actions.test.ts:17-23`; `computer-sessions.test.ts:30-36`). Marcar teste unitário, fixture protocolar e verificação live em campos separados.

## Contratos que devem ser preservados

- Toda rota de computador privada atrás de autenticação server-side; tokens de worker, supervisor, modelo e computador nunca no app. O gateway com política é o único caminho para ação de agente [1] [2] [10].
- Isolamento por identidade explicitamente escolhida, workspace/browser-profile persistentes e lifecycle verificável; nunca fallback para shell/arquivos do host. Manter a forte configuração Docker local e declarar o limite container-vs-VM (`apps/server/src/computer.ts:225-318,441-511`; [10]).
- Refs de elemento são opacas e sempre pareadas ao `snapshotId` e Bot alvo; refs antigas devem ser recusadas após navegação/restart/handoff, sem “adivinhar” elemento novo (`openbot/server/src/computer/routes.ts:278-300,939-955`; [8]).
- Política/receipt antes do side effect, auditoria da falha pós-dispatch, sem retry automático de `uncertain`; takeover é exclusividade, não uma tela visível nem uma fila de inputs.
- Control state precisa de `requestId`, estado terminal explícito e recuperação de restart. Secret entry é caminho separado: valor nunca em thread/receipt/log/screenshot; autorizar apenas campo apontado e não submeter automaticamente (`openbot/agent-computer/src/control.ts:166-189,279-299`; `openbot/agent-computer/src/index.ts:775-843`; [2] [4]).
- Manter browser e shell como capacidades separadas. O worker tem egress pública restrita e o Docker local não tem rede. Se egress for requisito, usar policy de rede por computador em vez de abrir sockets. Verificar também arquivos do usuário são dados não confiáveis, não instruções.
