# Auditoria S+ — threads, spaces e coordenação

**Veredito: não aprovar como coordenação S+ multiagente ainda.** O Whilo/O1 tem uma boa base de conversas duráveis e jobs assíncronos para um proprietário, mas threads, missões, tarefas e handoffs ainda não formam um grafo coordenado. Spaces/Pages não existem como modelo de domínio, Projects são apenas rótulos de escopo de memória, e os perfis de Agent não governam a execução do chat. **Nota neste eixo: 61/100** — forte em durabilidade single-agent; parcial em rastreabilidade de ponta a ponta; insuficiente em isolamento de contexto e coordenação multiagente.

## Findings

### 1. Rich Threads: fundação já útil, contexto organizacional ausente

**Já existe.** `ThreadsProvider` lê um `main-thread` estável do servidor; side chats recebem um UUID no cliente; a tela usa `useThreads` para listar, renomear, arquivar, restaurar e paginar conversas. O seletor exibe o chat principal e side chats, mas não tem filtros ou vínculos com Spaces, Projects, páginas ou agentes especialistas (`apps/mobile/src/threads.tsx:17-36, 47-91, 115-128, 150-279`). O chat cria um `useAgent` por `threadId`, conecta threads existentes para replay e preserva em memória a fila de follow-ups enquanto a tela está montada (`apps/mobile/src/chat.tsx:215-233, 290-329, 334-368`).

No servidor, `/api/main-thread` grava um único ID por proprietário e faz `getOrCreateThread` em Intelligence (`apps/server/src/app.ts:585-606`). O runtime resolve o usuário por `auth.owner`, desabilita o auto-naming e usa o agente `default` (`apps/server/src/agent.ts:27-61`). A configuração corrente expõe `richThreads: true` e exige a chave de Intelligence no servidor (`apps/server/src/workspace.ts:322-327`, `apps/server/src/config.ts:130`). O padrão de não copiar o transcript para a store local é bom: os cartões do chat guardam/reutilizam IDs de tarefas e buscam o estado/artefatos atuais pela API (`apps/mobile/src/thread-artifacts.tsx:62-90`).

**Parcial / risco alto de ciclo de vida.** Novos side chats ainda são seleção local até haver uma primeira execução; antes disso, `visited` é estado React e não um registro recuperável após refresh (`threads.tsx:69-91, 183-199`). A API principal persiste `existing: false` na criação, mas sempre responde `existing: true` (`app.ts:587-606`). O cliente usa esse booleano para decidir se chama `connectAgent` (`chat.tsx:302-309`), portanto o primeiro carregamento é tratado como replay mesmo quando o servidor acabou de criar a thread. O efeito exato depende do serviço Intelligence; falta teste de primeiro acesso com projeto real. Corrigir o retorno e cobrir “primeira mensagem / reload / reconnect” antes de apoiar fluxos críticos.

A fila de follow-ups é explicitamente volátil: `ConversationQueue` vive em memória, remove o item antes de enviá-lo e pausa após falha; não é uma inbox persistente (`apps/mobile/src/conversation-queue.ts:1-45`, `chat.tsx:232-233`). Isso é adequado como conveniência de composição, não como coordenação durável. O runtime de Intelligence documenta replay/catch-up de eventos, mas diferencia replay do transcript da retomada de estado/checkpoint do agente; execuções simultâneas no mesmo thread podem receber `409` [4]. O cliente tem `runLock` local, que não coordena dispositivos distintos.

**Já existe, mas deve ser tratado como legado separado.** `ChatScreen` ainda mantém um caminho não-Rich-Threads que lê/grava `/api/conversation` (`chat.tsx:302-312, 330-333`; `app.ts:608-616`). O runtime corrente marca Rich Threads como habilitado, então esse caminho não é o fluxo normal configurado; ainda assim, não se deve migrar silenciosamente mensagens entre os dois backends nem permitir que configuração de cliente escolha a fonte de verdade.

### 2. Conversation engine: idempotência por thread, não escopo por projeto/agente

**Já existe.** `ConversationAgent` recebe `threadId`, calcula `requestKey` com `threadId` e a última mensagem do usuário e usa chaves derivadas para idempotência de chamadas de ferramentas (`apps/server/src/engine/conversation.ts:29-45, 101-102`). `delegate_task` cria um job durável; o evento/ferramenta devolve o ID, e os cartões consultam o registro atual. A memória possui tipos de escopo, origem e proveniência.

**Parcial / risco alto de isolamento e auditoria.** A chamada de `createTask` passa proprietário, argumentos e chave de idempotência, mas não grava um FK navegável para `threadId`, mensagem de origem, Project, Space, Mission ou Agent (`conversation.ts:242-246`; `packages/domain/src/agent.ts:26-47`). A chave hash evita algumas duplicações, mas não substitui referências explícitas para auditoria, cancelamento, retorno de resultado ou recuperação. A lista fixa de ferramentas é construída no `ConversationAgent` e o runtime só publica um agente `default` (`conversation.ts:29-39, 109-111, 242-253`; `apps/server/src/agent.ts:33-50`).

O registro `O1AgentRegistry` já guarda `role`, `objective`, `modelPolicy`, `memoryScope` e `toolScopes` (`apps/server/src/o1/agent-registry.ts:7-18, 24-40`), mas a execução do chat não seleciona esse perfil nem filtra ferramentas pelo `toolScopes`. No estado atual, esses campos não são uma fronteira efetiva de autorização para o agente. Também há exemplos de perfis no UI que parecem mais completos do que o caminho de execução (`apps/mobile/src/agent-ui.tsx:1731-1733`). Não anunciar especialistas com ferramentas isoladas até que a seleção e a verificação aconteçam no servidor, na hora de construir cada execução.

**Risco crítico de “project memory”.** `project` é um valor aceito no enum, mas não há `projectId` no tipo de memória. `retrieve` lista todas as memórias do proprietário e filtra apenas pelo rótulo de escopo e texto, não por um Project concreto (`apps/server/src/o1/memory-engine.ts:5-18, 37-47`; `conversation.ts:334-345`). Assim, “project” não significa isolamento por projeto; memórias marcadas desse modo podem atravessar trabalhos distintos do mesmo proprietário. Até existir chave de escopo real, renomear/tratar esse valor como categoria não isolante ou deixar de o oferecer como promessa de separação.

### 3. Tarefas duráveis e missões: boa execução local, sem ligação à conversa

**Já existe.** `AgentService.createTask` valida a entrada, suporta idempotência, limita trabalho ativo, cria plano/checkpoints e persiste por proprietário (`apps/server/src/engine/service.ts:180-229`). `TaskWorker` varre registros, reivindica jobs com CAS/lease, limita o lote elegível a três e volta a tentar jobs com lease vencido; cria eventos e registra o resultado terminal (`apps/server/src/engine/worker.ts:64-115, 116-248`). Os estados de tarefa cobrem execução, espera por aprovação/input, pausa, sucesso, falha e cancelamento (`packages/domain/src/agent.ts:3-12`). Esse é o melhor ponto de partida para trabalho que continua após o app fechar.

**Parcial.** `AgentTask` tem `goalId`, mas não `threadId`, `projectId`, `spaceId`, `missionId` ou `agentId` (`packages/domain/src/agent.ts:26-47`). `StoredMission` guarda objetivo, orçamento, fase e checkpoint, mas não aponta para tarefas, thread, Space ou Project (`apps/server/src/o1/mission-store.ts:7-12, 17-28`). Existe um grafo puro de dependências (`apps/server/src/o1/task-graph.ts:1-40`), mas o worker executa o namespace `tasks` sem consultar esse grafo (`worker.ts:75-83, 111`); em código de produção, o módulo é exportado, não integrado como plano persistido (`apps/server/src/o1/index.ts:41`). Logo, hoje existem **jobs duráveis** e **registros de missão**, mas não uma orquestração durável de tarefas filho sob uma missão.

A UI já consegue reidratar cards e arquivos pelo ID da tarefa, mantendo URLs assinadas fora do transcript (`apps/mobile/src/thread-artifacts.tsx:62-105`; `docs/RICH-THREADS.md:22-28`). Preservar esse padrão: o histórico da conversa aponta para resultado canônico, não duplica o objeto da tarefa.

### 4. Handoffs: contrato e tela existem; despacho real, validação e concorrência faltam

**Parcial.** O contrato tipa destino como Agent ou humano e registra `missionId`, resumo, estado e status (`apps/server/src/o1/agent-handoff.ts:4-16`). Há rotas de criação/listagem/transição com owner autenticado (`apps/server/src/app.ts:266-275`) e um cartão para aceitar/cancelar (`apps/mobile/src/handoff-center.tsx:6-33`). A store de audit registra eventos de handoff.

**Ausente / risco alto.** `create` persiste o payload sem validar se missão/agente existem ou pertencem a um contexto permitido (`agent-handoff.ts:21-26`). Aceitar apenas muda status; não despacha tarefa/run para o agente. O `source`/`target` e `state` não carregam um contrato restrito de contexto ou um link obrigatório para thread/tarefa; `state` aceita qualquer objeto. A transição é leitura seguida de `put`, sem CAS/idempotência, apesar do restante do sistema ter `compareAndSwap`; duas transições concorrentes podem sobrescrever uma à outra (`agent-handoff.ts:29-37`). A tela só mostra pendentes e não oferece retorno de aceito para `returned` (`handoff-center.tsx:19-30`). Isso é um protótipo de caixa de entrada, não uma coordenação multiagente completa.

### 5. Comparação com OpenMuse, OpenDots e OpenBot

- **OpenMuse / Rich Threads:** o padrão de `useThreads` + `threadId` + `useAgent` é bom para conversas ricas e persistentes. A documentação oficial deixa claro que Intelligence armazena/reproduz eventos e que o framework continua dono do contexto/checkpoint de execução [1] [4]. A documentação do próprio Whilo/OpenMuse também explicita que a fila de follow-ups é local e que jobs delegados são separados do transcript (`docs/RICH-THREADS.md:20-30`). Adotar o thread como conversa — não como projeto, tarefa ou espaço de documentos.
- **OpenDots / Spaces:** Space é casa para páginas; Dot é um especialista independente que pode receber acesso a vários Spaces e tem destino padrão de páginas. Cada página e especialista podem ter thread própria. Páginas/metadados ficam na store do app e o histórico conversacional fica no Intelligence; os dois precisam de backup, mas não de cópia de conteúdo entre si [2] [3]. É o modelo mais próximo para biblioteca de trabalho, ainda que OpenDots seja um template alpha e não uma garantia de multiusuário ou colaboração realtime [2] [3].
- **OpenBot / channels:** um Channel representa superfície/roster de conversa e associação com um thread, não uma biblioteca de documentos. A implementação atual cria canal, membership, liga um ou mais agent IDs e persiste um `threadId` distinto; o fluxo direto faz find-or-create transacional para evitar canais duplicados [5] [6]. Channels SDK conecta agente e plataformas externas, mantendo modelo/ferramentas/lógica no runtime da aplicação e a entrega/conexão de plataforma no serviço gerenciado [7]. Usar `channelId`, `threadId`, `agentId` e ID da conversa externa como IDs distintos. O adapter OpenBot local continua desligado/não conectado: status `unconfigured` e `openbotConfigured: false` (`apps/server/src/workspace.ts:314-326`); a documentação local informa que o adapter é apenas uma seam contratual, sem round trip real (`docs/OPENBOT-INTEGRATION.md:53-76`).

## Modelo recomendado sem duplicar estado

Manter a divisão de autoridade simples. **Intelligence é dona do transcript/event stream do Thread. A store Whilo é dona de Projects, Spaces, Pages, Missions, Tasks, approvals e relações locais. OpenBot/Channels é dono do runtime/computer e do binding de canal externo quando conectado.** O Whilo mantém somente os IDs de ligação e os dados de produto que precisa pesquisar, autorizar ou apresentar; nunca espelha transcript, estado de computador ou credential do serviço externo.

- **Project (opcional):** agrupador operacional de longo prazo para um resultado ou iniciativa. Guarda nome/owner/descrição/estado; pode ligar-se a várias Spaces se esse uso existir. Não armazena cópias de páginas, conversas, tarefas nem configuração de agentes. Não criar Project para cada chat.
- **Space:** área de navegação e autorização para conteúdo persistente. Pages e artefatos têm um único local canônico; “mover” atualiza referência, não duplica conteúdo. Um Project pode ligar Spaces por uma relação, sem impor que Project e Space sejam sinônimos.
- **Mission:** objetivo executável dentro de um Project opcional, com orçamento e lifecycle; mantém plano agregado, não copia o estado detalhado de cada tarefa. `Task` é unidade de trabalho persistente; seu estado/lease/receipt vive em um único registro canônico e Mission agrega progresso derivado.
- **Agent:** perfil canônico do Whilo com identidade, versão de instruções/política e grants de ferramentas/Spaces. Cada `Run` referencia `agentId` e a versão efetiva. OpenBot `botId` é um binding externo, não o ID do Agent Whilo. Verificar grants no servidor antes de disponibilizar/executar ferramentas.
- **Thread:** conversa/event stream. Manter no Whilo um binding mínimo — `ownerId`, `threadId`, `runtimeAgentId`, contexto opcional (`projectId`, `spaceId`, `pageId`, `missionId`) e proveniência — sem armazenar mensagens. Página + Agent pode abrir um thread dedicado; uma conversa geral não deve herdar acesso a todas as Spaces por omissão.
- **Channel:** binding de ingress/egress para Slack/OpenBot/outro canal, com `channelId`, chave de thread externa, `agentId` autorizado e `threadId` interno. Nunca reutilizar `channelId` como `threadId` nem tratar um Slack channel como Space.

Relações são referências, não dados espelhados: `Project → Mission → Task/Run → Agent`; `Project ↔ Space → Page/Artifact`; `Thread ↔ Run/Task` via IDs de origem; `Channel → Thread/Agent` via binding. No começo, `projectId` deve ser opcional para manter trabalhos pessoais simples. Só materializar `ProjectSpace` muitos-para-muitos quando houver necessidade real de reuso; cada Page continua tendo um único Space proprietário. Versionar a política do Agent por execução é apropriado para auditoria, mas copiar configurações inteiras mutáveis para cada Task não é.

## Nós de implementação priorizados

1. **P0 — fechar o contrato de identidade e referência (parcial; valor muito alto; risco atual alto).** Definir IDs e relações `threadId`, `sourceMessageId`, `missionId`, `projectId`, `spaceId`, `agentId`, `runId` e `channelId`; adicionar validação de owner e integridade referencial na camada de serviço. Hoje `Store` é genérica (`owner/kind/id/data`) e não oferece FKs entre JSON records (`apps/server/src/db.ts:13-72`). **Dependências:** migração/adaptadores e regra explícita para registros legados órfãos.
2. **P1 — fechar lifecycle de Thread (base existente; valor alto; risco médio).** Corrigir o boolean `existing`; criar binding persistente para thread nova antes do primeiro turno, com idempotência; manter `useThreads`/Intelligence como fonte de nomes/arquivamento/transcript. Definir uma única rota ativa e política clara para o `/api/conversation` legado. Acrescentar testes de primeira mensagem, refresh antes/depois do primeiro turno, replay e duas telas/dispositivos simultâneos. **Dependências:** acesso a Intelligence de teste e autenticação estável.
3. **P2 — link origem → tarefa → resultado (durable Tasks existem; vínculo parcial; valor muito alto; risco alto).** Expandir schema de criação para referências de origem explícitas, gravar `sourceThreadId` + `sourceMessageId` e referências opcionais de missão/projeto/espaço/agente. Não reconstruir ligações a partir do hash de idempotência. Fazer Activity e card abrirem a mesma tarefa; publicar apenas referências/resultados necessários ao thread. **Dependências:** P0 e migração compatível de tarefas antigas.
4. **P3 — integrar Mission, grafo e handoff (parcial; valor muito alto; risco crítico antes de expor delegação).** Persistir nós/dependências e executar apenas batches prontos; validar mission/agent/owner em criação; fazer accept/return/cancel por CAS com idempotency key; ligar handoff a tarefa/run e thread de origem. Definir um packet tipado de contexto com resumo, evidências e IDs — sem transcript inteiro ou segredos — e uma regra de retorno/síntese. **Dependências:** P0/P2, ferramenta de dispatch, eventos auditáveis e política de depth/fan-out.
5. **P4 — materializar Space e Project e aplicar grants (ausente; valor alto; risco alto para dados privados).** Primeiro implementar APIs e autorização server-side; depois navegação Pages/Spaces e criação opcional de Project. Incluir `projectId` de verdade nas memórias e filtrar por Project; adicionar grants de Agent por Space e negar por padrão. **Dependências:** P0, estratégia de membership multiusuário e backup de metadata separado de Intelligence.
6. **P5 — conectar Channels/OpenBot após o modelo interno (adapter parcial, integração ausente; valor médio-alto; risco alto).** Fazer adapter server-side autenticado; mapear platform thread/channel → thread interno e Agent permitido; manter execução e computador atrás do gateway Whilo/OpenBot. Não enviar credenciais nem chamar computador diretamente do mobile. Testar identidade, reconexão, duplicação, cancelamento e resultado incerto. **Dependências:** P0–P3, bridge de sessão/identidade e deployment OpenBot fixado.
